Do not submit the app while it cannot initiate full account deletion.

## Implemented: native privacy screens and reauthentication (previous milestone)

- `app/account-deletion.tsx` is reachable from Account, sign-in, phone verification and the workspace-access fallback. It is outside paid/verified-customer navigation guards. Account switching immediately remounts the screen, clearing the previous account's review. No existing web or normal mobile authentication callback was replaced.
- A separate, non-persisted Supabase PKCE client verifies a method already linked to the server-verified account: email/password, Google or native Apple on iOS. It never calls `setSession` or `signOut` on the normal application client. The exact user UUID and original main-session ID are checked before/after verification and before sensitive requests. Email similarity is not an identity check and no account merge API is called.
- Google uses the dedicated `auth/deletion-callback` path, a random flow ID and the SDK's PKCE verifier. Normal-login callbacks, implicit access-token callbacks, duplicate/foreign parameters and closed flows are rejected. Callback handling and browser completion share one code-exchange promise. Cold-start recovery does not guess another client's verifier: it requires a fresh review.
- Existing verified TOTP/phone MFA factors can be challenged and verified; no factor is enrolled, changed or removed. Other required factor types fail closed with a support explanation. Fresh-proof expiry is at most five minutes, including MFA time; the frozen bearer is not replaced by a refreshed app token. Temporary sessions are discarded on exit/expiry, with best-effort local-scope revocation. An offline revocation attempt is not proof of server revocation.
- The page shows shared-account loss, project/asset/unfinished-job counts, customer/developer billing-provider warnings, privileged-workspace warnings, separate store cancellation links, two explicit acknowledgements, the exact typed confirmation and a countdown. A clearly labelled sample flow never requests credentials or sends network calls.
- The real journal is wired to device-only SecureStore (not AsyncStorage and not the auth chunk-store). Only the minimal receipt capability/status and an account-ID bookmark are persisted; not passwords, tokens, review counts or photos. Its namespace binds the environment and configured Auth/mobile origins. Browser live storage is refused. A signed-in account cannot browse another account's bookmark; signed-out recovery returns only minimal capability status.
- Storage writes and bookmark writes finish before mutations. Empty/corrupt/inconsistent records fail closed. Screen instances share serialized journal operations, preventing a reopened view from overwriting an in-flight capability. An uncertain confirmation is checked through status only. A saved preparation can resume using its same capability; a previously prepared review bound to a different temporary session must be cancelled before a new preparation.
- Native private transport uses Expo's streaming fetch, fixed HTTPS paths, bounded JSON, a timeout, `redirect:error`, no cookies and redacted errors. Receipt secrets appear only in POST bodies, never URLs. There is no automatic mutation retry.
- New read-only capability fields `accountDeletionReviewReady` and `accountDeletionRequestsReady` reflect the existing disabled flags. They cannot turn on `accountDeletionReady` or bypass the hard-coded processor gate. A reviewed/prepared request is explicitly not a submitted deletion.

Staging prerequisites: add the dedicated deletion redirect **alongside**, never instead of, the existing web/mobile callbacks. Test Google, Apple, password and enrolled MFA on both platforms, including a wrong provider account, cancellations, reinstall and signed-out receipt recovery. Review Supabase's single-session/time-box/CAPTCHA configuration: a project-level single-session policy may invalidate another session when any fresh sign-in occurs, and cannot be neutralized by a client option. Do not weaken existing Auth protections to make this flow pass. Complete Apple identity-grant revocation and all backend cleanup before enabling confirmation. The local mocked adapters and simulator demo do not certify real OAuth/MFA or store compliance.

## Implemented: account fence and bounded media cleanup (previous milestone)

`20260909085813_mobile_account_cleanup_fence.sql` is the **fourteenth unapplied mobile migration**. It adds two private control tables, permanent work guards and environment-gated media claim/acknowledgement RPCs. Applying it creates no deletion requests or fences and changes no existing customer rows. It does add shared-table triggers/restrictive policies, so staging schema, latency and regression acceptance are required before any shared deployment.

- Only a previously confirmed, queued request can begin cleanup. Active administrator identities stop at `ownership_review` without destructive action; a real ownership/retention resolution path remains required. Ordinary accounts become suspended, projects archived and unfinished jobs/steps cancelled under a per-user transaction fence. The fence survives feature-flag rollback and prevents reactivation or reassignment.
- Existing API webhook destinations are disabled **before** job cancellation, so the existing terminal-job trigger does not enqueue a cancellation webhook. Pending webhook deliveries are marked failed; live/sandbox keys are revoked and developer access ceilings/current access remain closed even during delayed package sync. Registered push installations are detached and pending pushes cancelled. Already-sent third-party deliveries cannot be recalled.
- New/updated projects, assets, jobs and room groups are rejected for a fenced identity. Additional restrictive ownership policies deny direct customer-work reads to a stale JWT. These are not a substitute for full Auth/provider revocation or a review of every other table/RPC. Shared advisory locks order normal writes around the fence; stronger-isolation transactions additionally lock the changed profile version so an old snapshot cannot bypass deletion.
- Three exact user prefixes cover original/output/mask objects. Job IDs are inventoried in pages of 200 for exact `tmp/<owned-job>/` prefixes. A job removed by retention after the fence preserves its scope before its ownership row disappears. No bucket-wide or loose-prefix sweep is used.
- The mobile Worker claims a two-minute lease and deletes at most one page of 200 objects per scope, at most five scopes per cron invocation. Every returned key is checked before **any** deletion; malformed responses, mismatched scope, expired leases and storage failures fail closed. Deletion is awaited before acknowledgement. It re-lists from the beginning rather than skipping through a changing deletion cursor.
- Storage outages back off five minutes. An untruncated empty list is only an observation, not completion. Two separated empty observations after the current two-hour quiet period advance to `external_cleanup_required`; hourly resweeps continue to catch late writes. The two-hour period is a defensive checkpoint, **not proof that providers/backups can no longer create copies**. Request receipts remain `queued`, never falsely `completed`.
- `MOBILE_ACCOUNT_CLEANUP_ENABLED=false` and database `cleanup_enabled=false` are independent gates. The unprovisioned `ACCOUNT_MEDIA` binding points only to `furnio-media-mobile-staging` with `remote:false`. No customer-callable cleanup endpoint is added. Already accepted work can be acknowledged during a flag rollback; the permanent fence does not disappear.

Still missing: a complete financial/identity/personal-data cleanup path, email/automation suppression and payload handling, reserved-credit resolution, provider cancellation/revocation, cache/backups/restore handling, operational alerts and completion evidence. Initial fencing uses set-based updates and needs large-account staging benchmarks and lock-retry checks. Do not enable request acceptance or treat a media sweep as full deletion. No live account or actual R2 file was deleted by these tests.

## Implemented: durable request and receipt (previous milestone)

`20260909083857_mobile_account_deletion_requests.sql` is the **thirteenth unapplied mobile migration**. It adds a private request journal and a narrowly granted action RPC. Existing customer/profile/login/payment/media rows are not changed by that migration. All destructive acceptance remains blocked by a code gate in addition to disabled Worker/database switches. **Do not enable database `processor_ready`: the complete cleanup processor is not implemented.** SQL tests temporarily enable it only in a disposable synthetic fixture.

- Preparation binds a short-lived nonce, notice version and review hash to the exact recently authenticated user/session/AMR/assurance. Its window cannot extend beyond the five-minute authentication lifetime. The complete read-only review is rechecked before confirmation; changed counts, linked providers, privileges or billing warnings require a new review.
- Confirmation requires `DELETE MY FURNIO ACCOUNT` and two explicit acknowledgements: shared account loss and separate subscription billing. Cancel applies only to unconfirmed preparation; a delayed cancellation cannot undo an accepted intent.
- One open request per user, transaction-scoped locking, a bounded lock wait, and a wall-clock freshness recheck prevent duplicate or stale acceptance. Ten new preparations per rolling day per existing account are allowed; idempotent retries do not use the limit or extend the window. No visitor/IP records are created.
- A client-generated UUID plus a random 256-bit secret is securely saved **before** the first network request. Only its SHA256 is stored in the database. Possession allows minimal status recovery, not login, review access or confirmation. The request has an Auth FK with `RESTRICT`, preserving its evidence until the retention workflow explicitly disposes of it.
- `POST /v1/account/deletion/prepare`, `/cancel` and `/status` are implemented. `/confirm` deliberately returns unavailable **before any mutation** while the processor code gate is false. Preparation also forces `canConfirm:false` regardless of remote settings. `accountDeletionReady` remains false.
- The status POST accepts only the UUID and receipt secret in a bounded JSON body, never a query string or account selector. It remains usable after app/request flags are rolled back and after sign-out. Unknown and wrong capabilities receive the same result. It returns timestamps and state only; no user ID, review, nonce or personal data.
- The native journal controller saves an uncertain confirmation as `confirming`. Restart, double tap and retry read the saved receipt instead of repeating the destructive operation. A racing `prepared` response does not falsely clear an uncertain confirmation. Corrupted secure storage fails visibly and is not silently replaced.

The request milestone implements persistence and the tested native controller; its screen/reauthentication adapter is now implemented as described above. The journal itself does not report `completed`, revoke tokens, erase files, cancel billing, or sign a customer out. Request/audit retention expiry remains unfinished. Public request/status rate limits are implemented locally in `ACCOUNT_PRIVACY_RATE_LIMITS.md`; real edge and native recovery acceptance still must pass before enabling this workflow.

## Implemented: read-only review (previous milestone)

- A mobile-only, read-only `GET /v1/account/deletion/review`, gated by `MOBILE_ACCOUNT_REVIEW_ENABLED=false` and a separately disabled private database setting. It cannot schedule deletion, suspend an account, cancel jobs/subscriptions, delete files or grant/recover credits.
- Fresh authentication proof: a maximum five-minute authentication-method timestamp, not a token-refresh `iat`, `last_sign_in_at`, supplied account ID or user metadata. Only password, OAuth, OTP or TOTP proof is accepted. Existing application login behaviour is unchanged.
- The same bearer token is verified at the configured Supabase Auth `/auth/v1/user` endpoint. The fixed project/origin is checked, redirects are prohibited, responses are bounded and staging cannot target the recorded production project.
- The service-only RPC independently checks the exact `auth.sessions` row and owner, `not_after`, current assurance level, matching `auth.mfa_amr_claims` method/time, a non-anonymous/non-deleted Auth user, and any enrolled verified MFA requirement. A logged-out or delegated OAuth-client session is rejected.
- Review is independent of customer-platform entitlement, paid status, phone verification and profile suspension. Those business restrictions must not deny the account holder their privacy controls. A banned Auth user still cannot bypass Auth verification.
- Response contains only counts, linked-provider names, grouped current billing warnings and whether shared developer/Admin roles exist. No email, address, photo, access token, store receipt, subscription ID or raw payload is returned.
- `canRequestDeletion` is hard-coded and schema-validated as `false`. Worker `accountDeletionReady` remains `false`; `POST /v1/account/delete` is still unavailable.
- The source inventory now covers all **120 declared public/private tables** in the Furnio main and Admin migration directories. `pnpm check:account-inventory` also detects any changed migration content, including altered columns/triggers, rather than checking only newly created tables. This is source coverage, **not** live-schema or cleanup certification.

The new migration is `20260909081654_mobile_account_deletion_review.sql`, generated with the Supabase CLI. It is the twelfth local mobile migration and is **unapplied outside the disposable synthetic test database**. It creates one disabled private settings table and one narrowly granted read-only RPC. No existing table data, authorization policy, login method or processing function is changed.

## Endpoint contract

`GET /v1/account/deletion/review`, no query or body. Authorization is the authenticated user's existing Supabase bearer token. Identity, session, environment, method and assurance are server-derived; client account selectors are not accepted.

Example response shape (illustrative counts only):

```json
{
  "version": 1,
  "scope": "shared_furnio_account",
  "canRequestDeletion": false,
  "accountAccess": "active",
  "counts": { "projects": 3, "storedAssets": 9, "unfinishedJobs": 1 },
  "subscriptions": [
    { "provider": "app_store", "context": "customer", "count": 1, "renewalNotCancelled": 1 }
  ],
  "hasDeveloperWorkspace": false,
  "hasAdministratorRole": false,
  "linkedProviders": ["apple"]
}
```

`storedAssets` counts non-purged asset records, **not every R2 object or every distinct photo**. Billing warnings are a snapshot of known records, not a live proof that a provider has cancelled renewal. Stripe developer and customer subscriptions are both included; native records are limited to the configured store environment.

401 requires signing in again. 409 means the database could not establish the current session/assurance, so sign in again and retry. Configuration/outage failures return 503; malformed provider responses fail closed. All responses use `no-store`. Browser Origin headers remain rejected. No caller identity, query, body, token or raw upstream error is logged.

6. **Complete media and personal-record cleanup.** Exact-prefix R2 paging, lease recovery and late-write resweeps are implemented locally, not certified against staging storage/providers. 7. **Billing after deletion.** Handle existing Stripe renewal responsibly, keep Apple/Google cancellation instructions explicit, retain only required payment/refund linkage, and process late verified financial events without re-enabling the account. 8. **Acceptance and rollout.** Staging provider revocation, both native platforms, multiple-device sign-out, cross-account attacks, recent-auth expiry, account switching, in-flight callbacks, deletion retries/outages, retention expiry and backups must pass. Add operational alerts and a customer completion confirmation. Keep destructive flags disabled until these gates and privacy acceptance pass.

## Current primary-source guidance

Supabase PKCE supports an explicit `sb_flow_id` when exchanging a code. The isolated adapter passes it to the installed SDK without changing the application's normal callback. [Supabase code exchange](https://supabase.com/docs/reference/javascript/auth-exchangecodeforsession). Existing MFA verification is distinct from enrollment. [Supabase MFA verification](https://supabase.com/docs/reference/javascript/auth-mfa-verify).

Expo SecureStore supports device-only keychain access and documents platform persistence differences; secure storage is not a substitute for server recovery/retention. The local journal is deliberately small and fails closed if storage is unavailable. [Expo SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/).

R2 supports exact-prefix bounded listing and awaited batch deletion. The implementation uses pages smaller than the documented limit and does not treat a short truncated page as proof of emptiness. [Cloudflare R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/).

PostgreSQL row-locking reads reject rows changed since a repeatable-read/serializable snapshot began. That additional check closes the stale-snapshot write bypass found by the fixture test; advisory locks alone are not enough. [PostgreSQL locking](https://www.postgresql.org/docs/current/explicit-locking.html).

Apple requires an in-app path to initiate full account deletion, with clear billing effects; deactivation alone is insufficient. Fresh confirmation is allowed, and Apple identity grants should be revoked. [Apple account-deletion guidance](https://developer.apple.com/support/offering-account-deletion-in-your-app/).

Supabase documents the JWT `session_id` relationship to `auth.sessions` and checking session existence for sensitive actions after logout. [Supabase sessions](https://supabase.com/docs/guides/auth/sessions).

Supabase exposes server-only deletion and an irreversible soft-delete option; that option alone does not clean application tables/media or certify this app's retention obligations. [Supabase admin deleteUser](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser).

Auth schema fields used in the preflight were checked against the official [sessions migration](https://github.com/supabase/auth/blob/master/migrations/20220811173540_add_sessions_table.up.sql), [MFA/AMR migration](https://github.com/supabase/auth/blob/master/migrations/20221003041349_add_mfa_schema.up.sql) and [session-expiry migration](https://github.com/supabase/auth/blob/master/migrations/20221114143122_add_session_not_after_column.up.sql). Full deployed-schema validation remains required.
